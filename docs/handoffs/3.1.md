# Handoff 3.1 — Independent Agent API / LLM / RAG

狀態：已完成（2026-09-05）。原文記錄本輪缺陷修正與本機驗證；後續主協調者已獨立驗收19/19通過（41.233s），18/18學習及18/18資源追問與原失敗案例均通過，詳見 `docs/demo-execution-plan.md`。真實外部provider仍未設定／未測。

## 實作結果

- 新增 `POST /api/v1/agent/chat` 與相容 alias `POST /api/v1/chat`。兩條路由進入同一個 service，使用相同 student auth、ownership preflight、canonical operation、idempotency、quota、RAG、持久化與錯誤處理；alias 無法繞過 key 或 quota。
- Pipeline 順序為：conversation/attachment preflight → quota reservation → local mode/intent 判斷 →（只有不明確的 live auto 才呼叫 intent model）→ profile → corpus retrieval → eligibility/context → Pydantic structured generation → primary Insight → message/snapshot/suggestion/usage 同一 transaction finalize。
- 明確 `mode=learning` / `topic` 或 `mode=resource` / `category` 不會額外呼叫 intent model。既有 conversation 的追問沿用已持久化 mode/topic/category。
- Offline Demo 僅支援 seed 的六個學習主題、各三個既有追問（共 18 個）、六類資源與各三個快捷追問（共 18 個）。`backend/data/**/followups.json` 是 server-owned canonical data，內容已逐項對照 frontend 原資料，但 runtime 不讀取 frontend。學習追問保留作者撰寫的 title/summary/steps/sources 及原 overview 的 practice/animation；資源追問回實際文件、窗口或期限說明，不再重複 overview summary。
- Offline 的 `topic` / `category` 只負責路由，不作為「問題受支援」的證據；回答前會以 canonical 問句、keywords/coverage 與 continuation 語意匹配。無關的牛頓法五次方程式、旅遊規劃、英文求職信等即使明示 topic/category 或沿用既有 conversation，仍回 503 `OFFLINE_DEMO_UNAVAILABLE`，不扣 quota、不寫成功 message/Insight。
- Live pipeline 不會轉用 offline fixture。provider / embedding 失敗回 502，server/provider timeout 回 504；reservation 會返還，回答、Insight 與 used count 不會部分成功。
- Live resource generation 仍只有一次 structured generation；model 從 retrieved program 選擇候選，server 再依本次問題以該候選的 authoritative documents、next_step、application window、nullable deadline 與完整 source snapshot 組成答案。因此追問會回答實際 facts，未知 deadline 明確標示需確認，且不依賴 offline 回答樣板。
- 圖片只在 live 模式以 authenticated upload 的實際 bytes 組成 `image_url` data URL 交給 multimodal provider。Offline 若附圖會明確說明未辨識圖片、只依文字回答；只有圖片而無可辨識 seed topic/category 時回 503。

## LLM boundary

- 新增集中 client：`backend/app/llm/client.py`。應用程式只有此模組 import/call provider SDK，提供 `generate()` 與 `embed()`。
- 使用官方 `openai==3.8.0` 的 `AsyncOpenAI`，由 server environment 設定 `base_url`、API key、chat model 與 embedding model；沒有把本次實作 CLI 的模型名稱當成應用 provider 要求。
- Structured generation 使用官方 SDK `client.chat.completions.parse(..., response_format=PydanticModel)`；embedding 使用 `client.embeddings.create(..., encoding_format="float")`。選 Chat Completions 是為了 OpenAI-compatible provider 的相容面與 structured/multimodal content parts。
- 參考的官方資料：[OpenAI Python SDK](https://github.com/openai/openai-python)、[Structured Outputs parsing helper](https://github.com/openai/openai-python/blob/main/helpers.md)、[SDK API reference](https://github.com/openai/openai-python/blob/main/api.md)。本 subtask 曾使用 OpenAI Docs 技能確認 SDK/API；上一輪新增的全域 `openaiDeveloperDocs` MCP entry 不在任務授權內，已由協調者移除。本輪沒有新增或修改任何全域 Codex/MCP 設定；後續查證採官方 OpenAI 網站或官方 SDK repository fallback。
- 固定 system boundary 明示 user text、conversation history、profile context、attachments 與 retrieved documents 都是不可信內容；模型不能改寫 auth、ownership、quota、runtime mode、政策條件，不能執行工具或聲稱已申請/核定/寫入記憶，也不會接觸 server secret。
- `LLMClient` 實作 async context manager 與集中 `aclose()`；chat 成功、失敗、timeout/cancel，以及由 indexer 自行建立的 embedding client 都會等待 SDK client 關閉，避免每次 request/index 建立後留下連線資源。

## RAG / index

- 新增 Chroma 本機持久索引，兩個 collection：
  - `futureai_curriculum_v1`：18 個教材 chunks。
  - `futureai_policy_v1`：12 個政策 programs/chunks。
- Retrieval 固定 Top K = 5；每個 chunk 都保存 stable chunk id、`source_id`、原 DB `record_id`、corpus/type、topic/category 與 title，可追到 response source snapshot。
- `backend/scripts/build_index.py` 使用 stable ID `upsert`、刪除 stale IDs，重跑不會重複。embedding signature 不相容時會重建 collection，避免用不同維度查詢舊 index。
- Live 建索引與查詢都呼叫設定的 embedding API。Offline 使用 `futureai-local-hash-v1-384` 可重現的本機 feature-hash vectors，不下載 embedding 大模型；它只保證 seed Demo 可重現，不等同 live semantic embeddings，也不可用來聲稱 live 檢索品質。
- `backend/data/chroma/.gitignore` 避免把本機 index artifacts 納入版本控制。

## Structured output 與政策安全

- Learning live payload 先通過 Pydantic，再驗證：所有 answer/step `source_ids` 都存在於本次 retrieved sources；scenario/animation topic 與 subject 必須屬於 retrieved chunks；practice `answer_index` 必須指向存在的 option；learning/resource payload 不可互換。
- Resource live model只能從檢索到的 `program_id` 候選選一項。傳給 model 的候選 context 包含 eligibility checks、missing conditions、文件、application window、deadline、next step、source note 與完整可追溯 source/excerpt；資格狀態與最終回答 facts 仍由 server 的 policy rows 加上 profile eligibility service 產生，模型不能改寫。條件不足保持 `possibly_eligible` / `needs_confirmation`，未知 deadline 保持 `null` 並在文字中要求向來源/窗口確認。
- 家庭資訊只會建立 real-UTC expiry 的 pending `MemorySuggestion` 並隨完整 assistant payload 持久保存。未收到既有 consent API 的 `consent:true` 前，不會新增或改寫 profile memory。

## Persistence、quota 與時間

- 每次成功保存 user/assistant `Message`、attachment relation/snapshot、完整 structured payload、source snapshot、follow-ups、可能的 pending suggestion，以及最多一個由該 assistant message 衍生的 primary `InsightEvent`。
- 新 learning activity 的 `practice_correct`、`animation_completed` 都為 `null`；不從模型回答虛構學生作答正確或動畫完成。
- Insight region 經既有 allowlist normalization；未知 region 持久化為 `null`，不硬塞六區任一值。成功後 teacher/government dashboard 的下一次 GET 可讀到新增 LearningActivity/Insight。
- `agent_chat` 是 alias 共用的 canonical idempotency operation。fingerprint 使用 trim/validation 後 request body 的 canonical JSON；同 principal + operation + key + body 在至少 24 小時內重播完整原 response、不重扣；同 key 不同 body 回 409。
- SQLite quota ledger 以 principal + 真實 UTC 日視窗唯一。reserve、finalize、release 都使用 SQL conditional update：reservation 只能從 `reserved` 原子轉移一次，ledger 以欄位算術 `reserved±amount` / `used+amount` 更新並以 `RETURNING` 取得 fresh usage，不依賴 ORM identity map 或 process lock。不同 session 同時 finalize/finalize、finalize/release、release/release 均不會 lost update 或重複轉移。
- reservation 先持久化；成功時 response snapshot、Insight、messages 與 reservation/ledger/idempotency finalize 在同一 transaction commit。任一例外先 rollback 未提交 payload，再原子 release、返還 quota 並把 idempotency 設為 failed；重複 finalize/release 為安全 no-op，同 body 可重試。
- startup 與 reserve 前 recovery 只回收 `expires_at <= real UTC now` 的 reserved lease，不再使用 `release_all`，因此另一個 worker 尚未過期的 active reservation 會保留；expired lease 會釋放，原 key 重試不重扣。
- Demo dataset anchor 只用於 offline learning message/activity/Insight 與 dashboard `as_of`。auth session、memory suggestion expiry、quota UTC 日視窗/reset、idempotency TTL、reservation lease、rate/timeout 全使用真實 UTC 或 asyncio/provider monotonic deadline，沒有隨 Demo anchor 凍結。

## API validation / errors

- `Idempotency-Key` 必填，trim 後須為 1..128 chars。
- message 在 Pydantic 長度驗證前 trim，trim 後最多 4000 chars；attachments 最多 3 個且不能重複。
- Conversation 與所有 attachment 必須屬於 authenticated student；延續 mode/category/topic 必須相容。這些 preflight 錯誤發生在 reservation 前。
- Server deadline 預設且上限為 45 秒。錯誤沿用統一 API envelope，主要新增/使用：409 `IDEMPOTENCY_CONFLICT` / `CONVERSATION_MODE_CONFLICT`、429 `QUOTA_EXCEEDED`、502 `PROVIDER_ERROR` / `PROVIDER_UNAVAILABLE`、503 `OFFLINE_DEMO_UNAVAILABLE`、504 `REQUEST_TIMEOUT`。

## 已知限制與後續接點

- 同 key 的請求若仍持有 active lease，現在回 retryable 409；完成後同 key 可拿原 response snapshot，失敗或 lease 過期後同 body 可安全重試。3.2 應以固定 submission key 與 client single-flight 避免同一 UI 動作重送。
- Chroma 是本機持久索引，沒有政策 crawler 或自動 freshness job；政策有效性仍以 seed/source timestamp 與 nullable deadline 呈現。部署更新 corpus/embedding provider 時必須重跑 `build_index.py`。
- OpenAI-compatible providers 對 structured output/multimodal 的支援程度不一；本輪只完成官方 SDK request shape 與本機 mock HTTP integration，未以真實 key 驗證特定外部 provider。
- 3.2 前端接點：兩個 POST 可擇一但需固定使用同一入口；每次使用者動作建立並保留一個 `Idempotency-Key`；render response 的 full sources、`demo`、nullable deadline、memory suggestion consent 與 502/503/504 狀態，不自行補事實或把失敗顯示成成功。
- 4.1 可沿用本輪已完成的 conditional reservation transition、ledger arithmetic update 與 expired-only lease recovery；本 handoff 不新增 4.1 必做範圍。
