## DB/schema 與 FK 決策

- Ownership：profile、memory/suggestion、conversation、upload、alert read 皆 FK 到 `users`；message ownership只經 conversation；message/upload 以 unique link table 關聯。
- `messages` 對 `(conversation_id, sequence)` unique；assistant message 保存 canonical structured payload、完整 source snapshot、follow-ups 與 attachment id snapshot，history replay 不需重新呼叫模型或重新檢索。
- `insight_events.message_id` unique nullable，保證單 message 最多一個 primary Insight。另可 unique 連結 `learning_activity_id`，並以 `(source_kind, source_reference)` 去重 provenance。
- Seed 不再按陣列索引把 unrelated activity/event 硬接到 message：3 筆 learning message 同時建立相符 activity 與 Insight；5 筆 resource message 依其 persisted `resource_recommendation.category` 建 Insight。獨立 authored observation 保持 `message_id = null` 並保留可追溯 source reference。
- Conversation delete：conversation → messages 使用 cascade；`profile_memories.source_conversation_id`、`memory_suggestions` 來源、`insight_events.message_id`、`learning_activities.message_id` 都是 `ON DELETE SET NULL`。因此刪除 history 不刪已同意 memory、不刪 Insight/learning evidence，也不改歷史 dashboard 統計。
- Consent/read 去重：`profile_memories(user_id, memory_key)` unique、`profile_memories.suggestion_id` unique、`alert_reads(alert_id, user_id)` unique。
- Teacher scope：`teacher_classes(teacher_user_id, class_code)` unique、`roster_students(class_id, seat_number)` unique、每個 roster row unique 連到一名 user。42 名虛構學生分為 801/802/803 各 14 人。
- Quota/idempotency：固定 `demo_principals.user_id` unique；ledger 以 `(principal_id, window_start)` unique，並有 nonnegative 與 `used + reserved <= limit` checks；reservation 一對一 idempotency record；idempotency 以 `(principal_id, operation, idempotency_key)` unique。Task 4.1 仍須完成原子 reserve/finalize/release service 與 session exchange。
- Policy 未知 `deadline`、`source_url`、`source_updated_at` 全為 null；提供 query hint 但不把它當 URL。所有 title/source note 清楚寫 Demo/資源方向，不聲稱政策現在仍有效。
- Government response schema 沒有 user/student/conversation/message/upload/profile 欄位；internal Insight 保留 user FK 供 ownership/teacher pipeline，但 government service 不可 join 或輸出它。

## 2.2 / 3.1 / 4.1 整合接點

### Task 2.2

- 從 `app.db.database.get_db` 取得 request-scoped session；從 `app.core.dependencies.get_app_settings` 取得 app settings。Router 掛在 `create_app()`，不要另建第二個 FastAPI app。
- 先建立 authenticated principal dependency，再開 profile/history/resource/alert/dashboard/upload route。契約保留 `user_id` 時仍須比對 session subject，不能直接信任 path/query/body。
- Core response 直接使用本階段 `app.schemas.*`，不要建立第二套 wire model。Conversation detail 從 `structured_response` + `source_snapshot` replay。
- Teacher aggregate 使用 `learning_activities`：question count 是 row count；practice denominator 只計 `practice_correct IS NOT NULL`；animation denominator 只計 `animation_completed IS NOT NULL`。新 chat 不增加兩個 denominator。
- Government aggregate 只查 `insight_events` 的 normalized region/government topic/resource flags，不 join users/messages。`resource_interest` 同時計 resource need + view；保持 `view <= need <= event`、`potential <= need`。
- offline Demo snapshot 使用 stored anchor 作 `as_of`；不要用啟動當天重寫 seed timestamp。Alerts 的 expires/null、policy deadline/url null 必須原樣保留。
- Upload metadata 已有 owner/storage key/hash/size/MIME；2.2 仍須完成 magic-byte 驗證、5 MiB、safe filename、private authenticated download 與實體檔 cleanup policy。

### Task 3.1

- `CurriculumScenario.answer_payload` 已是 `LearningAnswerWire`；`CurriculumMaterial` 與 `PolicyProgram` 可直接建 `SourceWire`，offline fixture 不必引用前端 data。
- Agent 成功 transaction 應一起持久 user/assistant messages、structured/source snapshot、至多一個 Insight 與 quota finalize；idempotent retry 不可重複寫任一項。
- 建 message-linked activity/Insight 時，owner 必須由 authenticated conversation 推導，topic/category 必須由同一個 persisted structured response 推導，`occurred_at` 使用該 assistant message 的 `created_at`；不可用列表索引配對 unrelated event。
- New learning chat 若只產生回答，可寫 linked learning activity/question row，但 `practice_correct`、`animation_completed` 必須 null；只有未來有真實 observation API 才寫 boolean。獨立 observation 不應偽裝成 message-derived event，必須使用自己的 source kind/reference。
- `/agent/chat` 與 `/chat` alias 共用同一 service、normalized operation key、quota/idempotency 與 persistence；不要複製 pipeline。
- Offline unsupported scenario 回 503；live provider failure 不可 fallback 成 Demo success。此階段尚未驗證任何 provider/embedding/RAG。

### Task 4.1

- `demo_principals` 只有 stable identity/config key，沒有 access code 或 token。Task 4.1 必須由 server secrets/config 完成 code 驗證與 opaque token hash，絕不可把 code/token 寫入 seed、log、URL 或 Vite。
- 以 transaction/conditional update 實作 `quota_ledgers` reserve，建立同 principal/operation/idempotency key record 與 reservation；成功後 finalize，未 commit 回答則 release。不要只依 process lock。
- 固定 quota key 是 principal + day window，不是 token/path/request user id；alias operation 必須 canonicalize，才能防止繞 quota。
- Schema 只有基礎 constraint，尚未實作 rate limit、session expiry/revocation、reservation recovery、access exchange 或角色 enforcement route。
